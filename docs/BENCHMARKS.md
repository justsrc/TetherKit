## Conclusions and analysis

### 1. Batch publishing still helps, but the gain is much smaller than the earlier record

Same queue, same transfer volume, changing only "how many frames per release
store":

| Frame size | batch=1 | batch=8 | batch=32 | Speedup |
|---|---:|---:|---:|---:|
| 1514 bytes | ~87 ns/frame | ~73 ns/frame | ~67 ns/frame | **about 1.3x** |
| 64 bytes | ~15 ns/frame | - | ~11 ns/frame | **about 1.4x** |

The reason is unchanged: a publish is a `release store` that bounces the cache
line holding the write index across cores once; batch publishing amortizes that
fixed cost by `1/N`.

Note: **the multipliers in this section do not match the early version of this
document (2.4x / 5.0x).** The difference comes from a machine change -- the
early numbers were measured on a different machine, this round on an Apple M5.
On M5 the cross-core cache-line bounce is much cheaper to begin with (`batch=1`
dropped from ~134 ns to 87 ns), so the part that can be amortized is smaller.
**The direction of the conclusion is unchanged (batch publishing is still a net
win and should always be used), but do not cite those two multipliers.**

> Implementation: `FrameRing::BatchWrite` / `BatchRead`. The data path must
> **always** use them; do not use per-frame `TryPush` / `BeginRead`.

### 2. The bottleneck really is system calls -- and more expensive than first estimated

The ~700 ns used earlier in this section came from an investigation with
`write(/dev/null, 1514)`, **not** a measurement on a real BPF descriptor. We
now have measured values, and **the measurement is about 3x the estimate**:

| Per-frame work | Cost |
|---|---:|
| RNDIS encode (including memcpy) | ~35 ns |
| RNDIS decode (zero-copy) | ~1.8 ns |
| FrameRing cross-thread transfer (batch=32) | ~67 ns |
| statistics counters | ~0.34 ns |
| **CPU total** | **about 105 ns** |
| one BPF `write()` (per frame, **measured**) | **about 2180 ns** |
| BPF batched write amortized per frame (>=32 frames, **measured**) | **about 805 ns** |

**A per-frame system call is more than 20x the CPU cost**; after batching it is
still 8x. This explains almost every key decision in the architecture:

- RX uses `BIOCSBATCHWRITE` to send a whole batch in one system call;
- TX uses RNDIS multi-packet aggregation so one bulk OUT carries multiple
  frames;
- `MaxTransferSize` is reported large in `INITIALIZE_MSG` (16 KiB by default
  instead of Linux's 2048), which is the only way to make the **device**
  aggregate multiple frames into one bulk IN;
- kqueue is never used for polling.

### 3. BPF write cost is almost independent of frame size -- which is why batching matters so much

| Write method | 1514 bytes | 64 bytes |
|---|---:|---:|
| per-frame `write()` | 2181 ns | 1934 ns |
| batched 32 frames | 805 ns/frame | ~728 ns/frame (batch=64) |

A 64-byte frame is only **13%** cheaper than a 1514-byte frame, while the data
volume differs by 23x -- meaning this cost is **almost entirely the fixed cost
of each call** (kernel entry, taking the BPF descriptor lock, going through
`bpf_movein` and the interface output path), largely independent of the number
of bytes actually moved.

The gain from batching saturates at **batch=32** (32/64/128 frames are
805 / 854 / 841 ns/frame, differences within noise). Larger batches only add
latency without buying throughput.

**This also gives a reassuring conclusion**: 805 ns/frame under batching is
about 1.24 million frames per second, about 15 Gbps at 1514 bytes -- while full
USB 2.0 High Speed needs only about 27,000 frames per second. **BPF writes are
far from this project's bottleneck**; even falling back to per-frame writes
(460,000 frames per second) leaves 17x headroom. The earlier worry that "BPF
writes determine the theoretical RX ceiling" can be put to rest.

### 4. The feth data-path round-trip latency is about 24 us

From writing an ARP request on the driver-side BPF to reading back the reply
from the system-side IP stack, the median is **24.5 us**. This includes two BPF
system calls, two crossings of the feth pair, and the peer IP stack's ARP
processing time. For comparison, host <-> phone ICMP round trips on the real
device are **about 400-600 us**, so this feth segment accounts for only
**about 5%** of end-to-end latency -- the bulk of the latency is in USB and on
the device side, not in the virtual interface.

### 5. Aggregation degree has almost no effect on encode/decode itself

RNDIS encode is 35.1 / 35.5 / 36.6 ns/frame at "1 / 4 / 10 frames per
transfer", and decode is 1.8 / 2.0 / 2.3 ns/frame. In other words, **the gain
from aggregation comes entirely from reducing system calls and USB round trips,
not from saving CPU**. The alignment requirement (`PacketAlignmentFactor`)
raises encode from 36.6 to 39.1 ns (one extra memset and MessageLength fill),
about 7%, which is negligible.

### 6. Decode is zero-copy; its "throughput" is not comparable to encode

The decoder only parses headers and returns views into the transfer buffer; it
moves **zero bytes**, so its throughput column is intentionally left empty
(`-`) in the table. Computing Gbps for it would produce absurd numbers in the
tens of thousands. Encode really does memcpy the whole frame; their ns/op values
are comparable, their Gbps are not.

### 7. relaxed load+store is 6x faster than fetch_add

Statistics counters use `relaxed load + store` (0.34 ns) rather than
`fetch_add` (2.04 ns). The difference comes from arm64's LSE atomic instruction
`ldadd`, which must obtain exclusive ownership of the cache line. Because each
counter has only one writer thread, we do not need read-modify-write atomicity.

The 1.7 ns saved per frame is negligible on its own; the real value is
**avoiding contention on the same cache line between the counters of the two
directions** -- once they contend across cores, the cost jumps from 2 ns to more
than 60 ns.

### 8. Unaligned reads are free

Parsing a 44-byte RNDIS header (11 `LoadLe32` calls, deliberately placed at an
odd offset) takes about 1.03 ns, about 0.09 ns/field. This confirms the claim
in `byte_order.h` that "`memcpy` + `byteswap` is optimized by clang into a
single `ldr`".

## Real-device end-to-end measurements

**Device under test**: vivo iQOO Z10x (model V2445A / PD2445M), Android 15
(SDK 35), USB `2d95:600b`, RNDIS interface signature `e0/01/03` (wireless
class variant), negotiated to **USB 2.0 High Speed**. iperf3 3.21 on the phone
was cross-compiled as a static arm64 binary with NDK r28; iperf3 3.21 on the
host. MTU 1500, the phone acted as gateway during testing
(`rndis0` = 192.168.35.7/24).

| Direction | TCP | UDP (flood 250 Mbit) |
|---|---:|---:|
| **RX** (device -> host) | **324~327 Mbps**, **0 retransmits** | - |
| **TX** (host -> device) | 234~241 Mbps, thousands of retransmits | delivered 142~161 Mbps, **35~43% drop** |

The theoretical effective payload ceiling for RNDIS over USB 2.0 High Speed is
about **426 Mbps**; RX reached **77%** of it.

### Three measured conclusions

**1) RX is clean; TX is the weak side.** RX stayed stable at ~325 Mbps in all
configurations with zero retransmits and zero frame drops; TX reached only
~235 Mbps on the same link with thousands of TCP retransmits.

**2) TX frame drops happen on TetherKit's own TX path, not due to device
rejection.** Runtime statistics provide direct evidence (with `--tx-transfers 4`,
the default):

```
TX 20213 pps / 244.82 Mbps (dropped 1889)  |  queue depth 0  kernel drops 0  backpressure 1155
```

`dropped` and `backpressure` increase in lockstep, showing that frames read
from BPF are being dropped because no free bulk OUT transfer is available.
**The root cause and fix are described in the next section** -- in brief, the
bridge discarded the rest of a batch as soon as the transfer pool was full
instead of waiting a few hundred microseconds.

**3) The TX problem is not RNDIS multi-packet aggregation.** The local Android
reported `MaxPacketsPerMessage=10`; there was a hypothesis that the device only
split the first packet (as mainline Linux gadget's `rndis_rm_hdr()` does).
Testing with the newly added `--max-tx-packets` A/B proved **that hypothesis
false**:

| packets aggregated per transfer | UDP drop rate | TCP TX |
|---|---:|---:|
| 1 (capped) | 42% | 125 Mbps |
| 3 | 43% | 237 Mbps |
| 10 (device-reported, default) | 35~58% | 234~241 Mbps |

Capping to 1 was **worse**. Aggregation is effective; the problem lies
elsewhere (see 2).

### Bidirectional concurrency collapsed TX to 4.8 Mbps before the fix

Before the fix, each direction was fine alone, but running bidirectional TCP
together produced:

```
[TX-C]  4.82 Mbits/sec   471 retr   cwnd 11.3 KBytes
[RX-C]  320  Mbits/sec     0 retr
```

TX collapsed to **4.8 Mbps**, about 1/50 of the unidirectional rate. The
mechanistic analysis at the time pointed to **bufferbloat**:

- UDP retests ruled out USB bandwidth contention -- with RX at full load and
  50 Mbit UDP injected concurrently, TX drops were only **0.32%** and the two
  directions together reached 348 Mbps;
- but full RX load pushed round-trip latency from **0.4 ms** idle to
  **16.6 ms** (40x);
- ACKs for the TX flow had to travel back over that saturated RX path, so the
  congestion window got stuck at 11 KB and `11 KB x 8 / 16.6 ms ~= 5.3 Mbps` --
  matching the measured 4.8 Mbps.

The arithmetic was correct, but it only explained the **consequence**. The
true first cause was why the cwnd got stuck at 11 KB -- it was because TX was
dropping frames. After fixing frame drops, bidirectional TX went straight back
to **87 Mbps** even though RTT inflation itself was not addressed. **So
bufferbloat was a secondary factor, not the root cause.**

## Root cause and fix for TX frame drops

**Root cause** (in one line): `Bridge::RunTransmitExtractor` **immediately
dropped** the rest of a batch when the USB transfer pool was full, instead of
waiting a few hundred microseconds.

The old code did `AddDroppedFull(remaining) + break` when `SendFrames`
returned 0 and carried a persuasive but factually wrong comment:

> Here we deliberately **drop** rather than wait: waiting would let the BPF
> kernel buffer accumulate and eventually be dropped by the kernel (and those
> drops would be invisible to us). Dropping in userspace and counting lets
> operators know what happened.

Neither premise holds:

1. **Kernel drops are not invisible.** `BpfLink::ReadFrames` reads
   `BIOCGSTATS` every batch and brings `bs_drop` back; it shows up in the
   statistics line under "kernel drops".
2. **The kernel buffer is exactly there to absorb bursts.** The default 4 MiB
   is about 130 ms of headroom at 250 Mbps; the transfer slots are freed every
   few hundred microseconds (once a bulk OUT completes). The old code refused
   to wait even a microsecond and dropped bursts that the 4 MiB buffer was meant
   to absorb.

The magnitude mismatch was extreme: the device reported 15800 bytes / 10
packets, so a 256-frame submission slice needs about **26 transfer slots** while
the pool has only **4**. Every slice was guaranteed to hit backpressure after
the 4th slot and drop the remaining ~200 frames on the spot -- that is what
caused the ~30%+ TX drop rate.

**Fix:** `SendFrames` now returns
`SendOutcome{consumed, sent_frames, sent_bytes, skipped}`; when
`consumed == 0` the bridge calls `WaitForSendCapacity(50ms)` to wait for a
slot (woken by the completion callback's condition variable), returns to the
top of the loop to recheck stop/pause flags, and retries -- **dropping zero
frames**. Any overflow falls back to the kernel BPF buffer, where it is dropped
only when full and remains visible in statistics.

### Fix effect (same device, default parameters)

| Metric | Before | After |
|---|---:|---:|
| TetherKit TX frame drops (6-8 s window) | 1889 | **0** |
| TCP TX retransmits | 3829 | **0** |
| TCP TX throughput | 234~241 Mbps | 239~302 Mbps |
| **Bidirectional TX** | **4.8 Mbps** | **87 Mbps** |
| Bidirectional RX | 320 Mbps | 240 Mbps |
| Unidirectional TCP RX (regression check) | 324~327 Mbps | 326~327 Mbps |

Two honest notes:

- **Bidirectional RX fell from 320 to 240.** This is not a regression but a
  restoration of fairness: before the fix TX was starved at 4.8 Mbps and RX
  monopolized the link; now both directions get their share and the aggregate
  went from 325 Mbps to about 327 Mbps -- total unchanged, allocation changed.
- **TCP TX is bimodal** (about 240 or about 300 Mbps, two stable states);
  both states were seen across three repeats and both have zero retransmits, so
  packet loss is not the cause. The reason remains unknown.

### Side conclusion: `--tx-transfers` no longer needs tuning

Before the fix, raising in-flight transfers from 4 to 16 cut drops to about 1/4
by compensating for the "refuse to wait" bug with pool depth. After the fix,
three repeats showed no distinguishable difference:

| `--tx-transfers` | TCP TX (3 runs) | Bidirectional TX | TCP RX |
|---|---|---:|---:|
| 4 (default) | 239 / 297 / 241, 0 retransmits | 87.8 / 86.6 | 327 |
| 8 | 298 / 238 / 297, 0 retransmits | 86.9 / 85.7 | 326 |
| 16 | 302 / 302 / 217, 1 retransmit | 86.2 / 89.6 | 326 |

**No discernible difference across the three settings.** The default stays at 4
-- pool depth should not be a throughput lever; it only needs to be enough to
overlap assembling the next batch with the previous batch in flight.

### A pitfall to remember: Android's `rx_errs` counter is not trustworthy

On the phone side, `/proc/net/dev` for `rndis0` counts wildly in
`rx_errs` / `rx_frame` (up to ~30-50% of packets received in measurements),
which easily looks like "the host is sending bad frames". **It is not.** A
low-rate counterexample proves it immediately:

```
50 pings -> 50 replies, 0% drop; but rx_pkts +51 and rx_errs +51 at the same time
```

Every frame is counted as both "received" and "error", yet replies are
completely normal. **When debugging TX issues, rely on iperf3's actual drop
rate and TetherKit's own statistics, not the phone-side `rx_errs`.**

## Measurement method and known limitations

- **Microbenchmark numbers are upper bounds for L1-resident data.** The real
  RX path's source is a USB DMA buffer just written by the device, which is
  cold in the CPU cache; the streaming memcpy measured in investigation is
  67-71 ns/1514 bytes, while the hot-cache memcpy in this document's tables is
  ~33 ns. Treat the CPU-side values in the tables as **lower bounds**. The
  link-layer group (BPF / feth) is not subject to this -- it measures real
  system calls.
- **The historical puzzle "RNDIS encode is faster than plain memcpy" has
  disappeared.** An earlier version of this document recorded an unexplained
  anomaly: encoding 1514 bytes measured ~14 ns/frame, faster than the
  ~25 ns for `memcpy` of 1514 bytes. Remeasured on Apple M5 in this round,
  encode is 35.1 ns / memcpy 32.9 ns -- encode is **slightly slower** than
  memcpy, as intuition would suggest (it is memcpy plus a 44-byte header). That
  anomaly should be attributed to the memory behavior of the earlier machine;
  it no longer reproduces and does not need further investigation.
- **High-spread items** (`SPSC cross-thread transfer`,
  `FrameRing single-thread round trip (64 bytes)`, `feth round-trip latency`)
  should be read as the **best round**. The reason is that spinning threads may
  be scheduled onto different mixes of performance and efficiency cores (this
  machine has 4 P + 6 E), and macOS provides no CPU affinity interface
  (`thread_affinity_policy` is effectively useless on Apple Silicon).
- **The link-layer benchmarks require root.** When run without root, the group
  does not disappear silently; the report records "Not measured in this run".
  To measure: `sudo ./build/bin/tetherkit_bench > docs/BENCHMARKS.md`. Note
  that the fixture must be torn down explicitly before `main` returns
  (`ShutdownNetBenchmarks`) -- leaving it to static destructors throws because
  the logging mutex has already been destroyed, which shows up as "all
  benchmarks finished but exit code 134".
- A measurement mistake was caught earlier: the statistics counter initially
  measured **0.00 ns/op** because the compiler is **allowed** to coalesce
  consecutive relaxed read-modify-writes (fold N times +1 into a single +N).
  Adding a `ClobberMemory` compiler barrier produced the true 0.34 ns. Every
  benchmark in this project must therefore ask itself: "did the measured work
  actually happen?"

## A pitfall in the stress-test environment: the privilege-escalation chain swallows SIGTERM

The `osascript ... with administrator privileges` escalation chain **swallows
inter-process SIGTERM delivery**: `kill -TERM $pid` in the script returns 0,
the target process shows `blocked` / `pending` masks of 0, and the
`sigaction`-installed handler is indeed in place (`sample` shows the handler
address is not `SIG_IGN`), yet the signal never arrives and the process can
only be killed with `kill -9`.

A 15-line C program confirmed this independently of TetherKit:

| Execution environment | Receives SIGTERM? |
|---|---|
| plain shell | yes |
| plain `osascript do shell script` | yes |
| `osascript ... with administrator privileges` | no |

**Consequence: do not use this chain to verify graceful shutdown.** It produces
a "shutdown hangs" false failure that has nothing to do with the code under
test -- logs before and after the fix were all `Killed: 9`. To verify
end-to-end shutdown, run `sudo build/bin/tetherkit-cli` in a real terminal and
press Ctrl-C (verified this way, as noted above).
