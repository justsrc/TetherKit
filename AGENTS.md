## 1. One-sentence project summary

A macOS **userspace** RNDIS driver: on the USB side it uses libusb to talk to RNDIS devices (Android USB tethering, etc.); on the network side it uses a `feth` virtual interface pair plus BPF to read and write raw Ethernet frames directly, turning the device into a network interface visible to the system.

### 2.3 BPF (Darwin)

| Fact | Conclusion |
|---|---|
| **Zero-copy BPF** | **Does not exist**. The SDK's `net/bpf.h` has **no** `BIOCSETZBUF` / `BIOCGETZMAX` / `BIOCROTZBUF` (FreeBSD has them, Darwin does not). Only classic BPF is possible: large `BIOCSBLEN` + batched `read()` |
| Full set of available ioctls | `BIOCGBLEN`(102R) `BIOCSBLEN`(102WR) `BIOCSETF`(103) `BIOCFLUSH`(104) `BIOCPROMISC`(105) `BIOCGDLT`(106) `BIOCGETIF`(107) `BIOCSETIF`(108) `BIOCSRTIMEOUT`(109) `BIOCGRTIMEOUT`(110) `BIOCGSTATS`(111) `BIOCIMMEDIATE`(112) `BIOCVERSION`(113) `BIOCGRSIG`(114) `BIOCSRSIG`(115) `BIOCGHDRCMPLT`(116) `BIOCSHDRCMPLT`(117) `BIOCGSEESENT`(118) `BIOCSSEESENT`(119) `BIOCSDLT`(120) `BIOCGDLTLIST`(121) `BIOCSETFNR`(126) |
| `struct bpf_hdr` | `{ struct BPF_TIMEVAL bh_tstamp; bpf_u_int32 bh_caplen; bpf_u_int32 bh_datalen; u_short bh_hdrlen; }` -- traversal **must** use `bh_hdrlen`, not `sizeof(bpf_hdr)` |
| Alignment macros | `BPF_ALIGNMENT = sizeof(int32_t) = 4`, `BPF_WORDALIGN(x) = ((x)+3) & ~3` |
| Device nodes | `/dev/bpf0..3` exist (Darwin clones more nodes on demand) |
| **Batch write** | Supported (macOS 14+): private ioctl `BIOCSBATCHWRITE = _IOW('B',143,int) = 0x8004428f`. The buffer format is symmetric with read (consecutive `bpf_hdr + frame`, each aligned by `BPF_WORDALIGN`), with the prerequisite `BIOCSHDRCMPLT=1`. macOS 13 and earlier **do not have** this ioctl -> runtime feature detection is required, falling back to per-frame write on failure |
| Private ioctl numbers (verified on real hardware) | `BIOCSBATCHWRITE`=0x8004428f, `BIOCSNOTSTAMP`=0x80044291 (disable timestamps, saving one microtime per frame), `BIOCSWRITEMAX`=0x8004428c, `BIOCSDIRECTION`=0x8004428a, `BIOCSHEADDROP`=0x80044280. macOS 26 moved them from `net/bpf.h` to `net/bpf_private.h` (**that file is not provided by the SDK**) |
| `BIOCSBLEN` upper bound | `sysctl debug.bpf_bufsize_cap` = **33554432 (32 MiB)**. Exceeding it does **not** report an error; it is silently clamped and the actual value is **written back into the argument** via `_IOWR` |
| `read()` buffer length | **Must exactly equal** `bd_bufsize`, otherwise `bpfread` returns `EINVAL` at the start. The written-back value from `BIOCSBLEN` must be used |
| `BIOCSHDRCMPLT` | **Must be set to 1**. =0 makes `bpfwrite` strip the first 14 bytes and rebuild the frame header (the source MAC is rewritten by the driver); =1 takes the `DLIL_OUTPUT_FLAGS_RAW` path and passes the frame through unchanged. Batch write also requires it to be 1 |
| Single-frame write length limit | `BPF_WRITE_LEEWAY = 18`; with `hdrcmplt=1` the total frame length must be <= interface MTU + 18 (MTU=1500 -> 1518) |
| `BIOCSRTIMEOUT` resolution | **10 ms** (the kernel stores `tvtohz(tv)-1` ticks; `kern.clockrate hz=100` measured on real hardware). Passing `{0,0}` becomes a **permanent block** |
| Optimal read model | `BIOCIMMEDIATE=1` + a **dedicated thread blocking on `read()`**, do not use kqueue. With immediate, every arriving packet wakes the reader, and when `read()` wakes it delivers all packets accumulated during that interval at once (low latency at low rate, automatically large batches at high rate, behavior similar to NAPI), with only one system call per batch; kqueue has the same readiness criterion but costs an extra `kevent()` |
| `/dev/bpf` clone node | **Does not exist** (`ls /dev/bpf` -> No such file, measured on real hardware). `/dev/bpf%d` must be tried in order: try the next on `EBUSY`, stop at the limit on `ENOENT`. Opening the current last node causes the kernel to create one more on demand. Limit `sysctl debug.bpf_maxdevices` = 256 |
| `access_bpf` group | macOS **does not have one** (that is the FreeBSD approach; `dscl . -list /Groups` had no match on real hardware). `/dev/bpf*` is `0600 root:wheel`, so only root can open it |

### 2.4 feth (if_fake)

| Fact | Conclusion |
|---|---|
| Present | **Yes**, visible via `sysctl net.link.fake.*` |
| Key sysctls | `net.link.fake.max_mtu = 2048`, `tx_headroom = 32`, `buflet_size = 512`, `qset_cnt = 4`, `link_layer_aggregation_factor = 96` |
| Creation permission | **Requires root**: as a non-root user, `ifconfig feth0 create` returns `SIOCIFCREATE2: Operation not permitted` |
| `struct ifdrv` | **Not in** the public SDK's `net/if.h`; it must be declared manually. With `#pragma pack(4)`, `sizeof == 40` on LP64 (offsets 16/24/32). **The size participates in ioctl number calculation**; getting it wrong yields a non-existent ioctl number -> pinned down with `static_assert`. Measured `SIOCSDRVSPEC = 0x8028697b`, `SIOCGDRVSPEC = 0xc028697b` |
| `net/if_fake_var.h` | **Not in** the public SDK. `struct if_fake_request` = `uint64_t reserved[4]` (32 bytes, **the kernel requires all zeros**) + a 128-byte union, **160 bytes total**. `IF_FAKE_S_CMD_SET_PEER = 1`, `IF_FAKE_G_CMD_GET_PEER = 1` |
| Private ABI version risk | **Very low, no need to fall back to ifconfig**: the md5 of `if_fake_var.h` is identical across every release tag from xnu-7195 (macOS 11) to xnu-12377 (macOS 26), never changed. Apple's own `ifconfig fethN peer fethM` takes this same ABI path |
| SET_PEER kernel checks | Five checks; failure of any returns `EINVAL`: (1) `ifd_len >= 160`; (2) `reserved` all zero; (3) the peer must also be feth (`ifnet_name()=="feth"` and `IFT_ETHER`); (4) neither side may already have a peer; (5) root is required |
| **Data-flow semantics** (confirmed against the `feth_output_common()` source) | A frame the host sends from feth0 -> is in the **input** direction on feth1; a frame we `write()` into feth1's BPF -> takes feth1's output path -> enters feth0's **input** -> is received by the host IP stack, and **does not** loop back to feth1. So BPF only needs to attach one descriptor to feth1 to both receive and transmit |
| Effect of `BIOCSSEESENT=0` | -> `bd_direction = BPF_D_IN`, which filters out exactly **the frames we ourselves wrote** (they are in the output direction on feth1). **Not setting it creates a loop** |
| `IFF_UP` requirement | `bpfwrite` has a hard check `if ((ifp->if_flags & IFF_UP) == 0) return ENETDOWN` -> feth1 must be UP; feth0 must also be UP so the IP stack can process received frames |
| **Sysctl snapshot at creation time** | Warning: `hwcsum` / `fcs` / `tso_support` / `lro` / `trailer_length` / `separate_frame_header` / `max_mtu` and similar switches are snapshotted into the interface at the moment `feth_clone_create()` runs; **changing the sysctls after creation has no effect**. If `hwcsum=1`, the frame checksums we read are placeholder values left for hardware to compute. On this machine the defaults were all 0 on real hardware (exactly what we want), but the code still validates them explicitly before creation (`VerifyFethSysctls()`) |
| Kernel-assigned MAC | `'f','e','t','h', unit>>8, unit&0xff` -> feth0 = `66:65:74:68:00:00` (bit 1 of 0x66 is set -> locally administered address, valid) |
| MAC-setting strategy | The **system side** (feth0) MAC should be set to the device-reported `OID_802_3_PERMANENT_ADDRESS` (in RNDIS semantics the device is this network interface; peers build ARP/DHCP state from it); the **driver side must keep its different kernel-assigned MAC**, otherwise the two sides would have identical IPv6 link-local addresses and trigger a DAD conflict. The MAC must be changed before `IFF_UP` |
| `BIOCPROMISC` | **Not needed** for feth: `feth_output_common` unconditionally delivers frames to the peer and taps without MAC filtering; whether a frame is readable is determined only by direction |
| DHCP | `sudo ipconfig set feth0 DHCP` (a temporary service that lives only until the next network configuration change and does not appear in System Settings). Teardown: `sudo ipconfig set feth0 NONE`. `networksetup` cannot be used -- feth is not in the `SCNetworkInterface` list |
| Performance ceiling warning | Community reports show the feth path can hit kernel mbuf overflow and panic above roughly 5-8 Gbps. Risk to this project is low: RNDIS over USB 2.0 HS measures about 200-300 Mbps, and even over USB 3 it is hard to exceed 1-2 Gbps |
| Relevant ioctls (**present** in the public `sys/sockio.h`) | `SIOCSIFFLAGS`(i,16) `SIOCGIFFLAGS`(i,17) `SIOCSIFMTU`(i,52) `SIOCSIFLLADDR`(i,60) `SIOCIFCREATE`(i,120) `SIOCIFDESTROY`(i,121) `SIOCIFCREATE2`(i,122) `SIOCSDRVSPEC`(i,123) `SIOCGDRVSPEC`(i,123) |
| `IFNAMSIZ` | 16 |

### 2.5 Development-environment constraints (affect the test strategy)

- **No root**: the current session runs as uid 501 and cannot create feth or open `/dev/bpf*`.
  -> Tests that need root must be **optional and skippable**, controlled in CI and locally by a switch such as `TETHERKIT_ROOT_TESTS=1`.
- **No guarantee of a USB device**: at project start the development machine had none, and a real device was only connected later for verification.
  -> The USB backend must be abstracted behind an interface with an in-memory loopback mock; end-to-end tests and throughput benchmarks run on the mock.
  Automated tests **must not depend on a device being present**.
- Verification status and items still unverified are recorded together in section 6 of this file.

Dependencies are **strictly one-way**; reverse or cyclic dependencies are forbidden:

```
tk_common  <- (no dependencies)
   ^
tk_rndis / tk_net / tk_usb  <- tk_common
   ^
tk_core    <- common + rndis + net + usb
   ^
tetherkit (executable) <- core
tk_capi (C ABI)        <- core          -> packaged as the shared library libtetherkit
   ^
gui/ (Swift)           <- libtetherkit
```

The Swift side can only see `libtetherkit`, never any C++ symbol (the export symbol allowlist is pinned to `_tk_*`). The C++ layer's interfaces use `std::expected` / `std::span` / abstract base classes, which Swift's C++ interop cannot consume, so the C ABI layer is not optional.

## 4. Code conventions (consistent with CheckOptions in `.clang-tidy`)

| Category | Convention | Example |
|---|---|---|
| Namespace | `lower_case` | `tetherkit`, `tetherkit::rndis` |
| Types (class/struct/enum/alias) | `CamelCase` | `RndisStateMachine`, `BpfLink` |
| Functions and methods | `CamelCase` | `SendEncapsulatedCommand()` |
| Local variables and parameters | `lower_case` | `frame_len`, `max_transfer_size` |
| Private/protected member variables | `lower_case_` with trailing underscore | `handle_`, `request_id_` |
| Constants (global/constexpr/enum values) | `k` + `CamelCase` | `kMaxFrameSize`, `kCacheLineSize` |
| Macros | `UPPER_CASE` (avoid macros when possible) | |
| File names | `snake_case`, `.cc` for implementation, `.h` for headers | `spsc_ring.h`, `bpf_link.cc` |

Error handling by layer:

- **Initialization / control path**: `std::expected<T, Error>`, where the error can carry errno / libusb error code / context string.
- **Data hot path**: **never** return `expected`, never throw, never allocate. Use return counts plus atomic statistics counters to express failure.
- `-fno-exceptions` everywhere? **No** (doctest needs exceptions), but the project's own code does not `throw`.

### User-facing strings and language

**User-facing text is never written as a literal**; it all goes through the message table. Two implementations, the same mental model:

| | C++ (library + CLI) | Swift (GUI + helper) |
|---|---|---|
| Message table | `include/tetherkit/common/messages.def` (X-macro, expanded into an enum + one table) | `gui/Sources/TetherKitIPC/LocalizedStrings.swift` (exhaustive switch) |
| Look up a string | `Tr(Msg::kFoo, args...)`, arguments match `std::format` | `L(.foo, args...)`, `String(format:)` printf style |
| Log | The `TETHERKIT_INFO_TR(Msg::kFoo, ...)` family of macros | -- |
| No arguments | `Text(Msg::kFoo)` returns `string_view`, no allocation | `L10n.text(.foo)` |
| Missing a language | Table-length assertion + `common.i18n` case | **Fails to compile** (exhaustive switch) |
| Placeholder mismatch | `common.i18n` checks indices and types per entry | `LocalizationTests` checks position and type per entry |

Three hard rules:

1. **Forbidden on the hot path.** `Tr()` / `L()` both allocate and format; like `error.h`, they may appear only on the initialization and control paths. When the hot path needs text, use `Text(Msg::kFoo)` (pure table lookup, noexcept).
2. **Placeholders must correspond one-to-one across languages** (count, index, type). When word order differs, reorder with explicit numbering: `{0}`/`{1}` in C++, `%1$@`/`%2$ld` in Swift.
3. **On the Swift side integers are always `%ld` and converted to `Int` at the call site.** `%d` takes only the low 32 bits of a 64-bit argument.

Where the language comes from:

- CLI: `--lang en|auto`; when omitted, inferred in order from `TETHERKIT_LANG` -> `LC_ALL` -> `LC_MESSAGES` -> `LANG`. **The language is fixed before arguments are parsed**, so help text and argument errors themselves are in the target language. Warning: sudo does not necessarily pass these variables through; in that case pass `--lang` explicitly. Any other value is rejected with "unknown language ...; English is the only language shipped today".
- GUI: the language switch in the App menu and the menu bar panel (Follow system / English), stored in the `TetherKitLanguagePreference` UserDefaults key.

**All three places must be updated together when the language changes; missing any one leaves "the UI in English, the logs in Chinese"**: the Swift string table (`L10n.apply`), libtetherkit (`tk_set_language`), and the helper (XPC `setLanguage` -- it runs as root under launchd and cannot see the user preference). All three are done together in `AppModel.applyLanguage`; do not call any one of them alone elsewhere.

The string table currently has one column (English). The CLI accepts `--lang en` (and `auto`, which also resolves to English) and rejects every other value. The GUI menu offers "Follow system" and "English". The multi-language plumbing (the `Language` enum, `TextIn`, `ParseLanguage`, the C ABI `tk_set_language`, the helper's `setLanguage` XPC method, `L10n.apply`) is deliberately kept so that adding a language later stays a bounded five-touch change; the checklist lives at the top of `include/tetherkit/common/messages.def`.

## 6. Verification checklist (needs root or a real RNDIS device)

### 6.1 Verified: USB side (**no root required**)

Measured on a real RNDIS device. The conclusions are recorded as platform facts -- they reflect macOS/libusb behavior, not a specific device model.

**(1) As a non-root user, `libusb_open` does not return `LIBUSB_ERROR_ACCESS`; it succeeds directly.**

The earlier assumption was wrong. Opening a USB device on macOS **does not require root** (unlike the Linux udev permission model). The entire USB side -- enumeration, `libusb_open`, interface claim, transfer I/O -- can run as a normal user; root is needed **only** to create feth and open `/dev/bpf*`. `--list` therefore states explicitly that it "does not require root".

**(2) Warning: `libusb_kernel_driver_active() == 1` on macOS does not predict that `claim` will fail.**

This is the easiest mistake to make in this section. Measured on the same composite device:

| Interface signature | Matched driver | `kernel_driver_active` | `libusb_claim_interface` |
|---|---|---|---|
| `02/02/ff` RNDIS communication | **None** | 0 | Succeeds |
| `0a/00/00` RNDIS data | `AppleUserECMData` (DriverKit dext) | **1** | **Still succeeds** |
| `02/02/01` CDC-ACM control | `AppleUSBACMControl` (kext) | 1 | `LIBUSB_ERROR_ACCESS` |
| `03/00/00` HID | `AppleUserUSBHostHIDDevice` | 1 | `LIBUSB_ERROR_ACCESS` |
| `ff/42/01` vendor-specific | Present | 1 | `LIBUSB_ERROR_ACCESS` |

`kernel_driver_active` only reflects that a driver **matched** the interface in IOKit; it does **not** indicate whether that driver **exclusively holds** the interface. After matching the `0a/00/00` data interface, the DriverKit dext (`com.apple.DriverKit.AppleUserECM`) does not hold it exclusively, so claim still succeeds; kexts (ACM/HID) do hold exclusively.

**Therefore: do not use `kernel_driver_active` as a preflight check and fail early**; that would misclassify a usable device as unusable. The only reliable test is to claim and inspect the return value. And because macOS has no `libusb_detach_kernel_driver` (see pitfall 7 in section 7), a claim failure really is unrecoverable.

The good news is that the RNDIS **communication** interface (`02/02/ff`) has no driver match at all -- confirming the project-start assumption that "macOS has no RNDIS kernel driver".

How to reproduce: use `--list` to see recognition results; for interface-level detail, inspect driver matches with `ioreg -c IOUSBHostInterface -r -l`, then claim each interface in a short libusb program of about a dozen lines and inspect the return values.

**(5) The effective `BIOCSBLEN` ceiling is 32 MiB; `debug.bpf_maxbufsize` is not its constraint.**

Measured in `BIOCSBLEN` -> `BIOCSETIF` -> `BIOCGBLEN` order (reading back the **effective** value after attaching to the interface):

| Requested | Effective value after attaching |
|---|---|
| 4 KiB / 1 / 4 / 8 / 16 / 32 MiB | Takes effect unchanged, byte for byte |

(`debug.bpf_bufsize` does correctly report the 4 KiB default.) Also, 32 MiB being "settable" is not the same as "worth setting that high": the default 4 MiB is already enough.

**(6) A BPF `write()` really does let the peer feth's IP stack receive a frame -- the core assumption of the whole approach holds.**

Verified with an ARP round-trip loop: the system-side feth is assigned `10.99.99.1`; from the **driver-side** feth's BPF we write an ARP request asking for `10.99.99.1`, and immediately read back an **ARP reply** from the system-side IP stack on the same BPF (source MAC is exactly the system-side feth's MAC, claiming to own that IP).

This single experiment proves two things at once:

- `write()` to the driver side -> the frame crosses the feth pair -> the **peer IP stack really receives and processes it** (otherwise it would not reply);
- loopback suppression with `BIOCSSEESENT=0` is correct -- only the input-direction reply is read back, not the request we just wrote.

Warning: this path has a prerequisite; see pitfall 14 in section 7 (`BIOCSHDRCMPLT`).

**(7) End to end: RNDIS handshake -> feth pair creation -> BPF attach -> graceful shutdown, the full path works.**

Key milestones from one complete startup: interface claim yields bulk IN/OUT (`wMaxPacketSize` 512) and interrupt IN -> RNDIS negotiation completes (version 1.0, MTU 1500) -> device MAC and link speed are read -> the state machine enters "data plane ready" -> the feth pair is created and paired, the system-side MAC is changed to the device MAC -> BPF attaches to the driver side.

After `SIGTERM` the teardown order is correct, **no feth interfaces are left behind, and the default route was never changed**.

### 6.5 Fixed: TX frame drops under high load

**Root cause in one line**: `Bridge::RunTransmitExtractor` **immediately dropped** the rest of the batch when the USB transfer pool was full, even though a slot would become available in a few hundred microseconds.

The old code did `AddDroppedFull(remaining) + break` when `SendFrames` returned 0, with the rationale "waiting would let the BPF kernel buffer pile up into **invisible** kernel drops; better to drop in userspace and count it". Both premises were wrong: `bs_drop` is read back by `ReadFrames` on every batch and is shown in the "kernel drops" column of the statistics line; and the 4 MiB kernel buffer (~130 ms of elasticity at 250 Mbps) is **exactly** the level that should absorb bursts. The numbers make it clearer: the device reports 15800 bytes / 10 packets, so one 256-frame submission slice needs about **26 slots**, while the pool holds only **4** -- every slice was guaranteed to hit backpressure after the 4th slot and drop the remaining 200+ frames on the spot.

**Fix**: `SendFrames` returns `SendOutcome{consumed, sent_frames, sent_bytes, skipped}`; when `consumed == 0` the bridge calls `WaitForSendCapacity(50ms)` to wait for a slot (the completion callback wakes a condition variable), then returns to the top of the loop to recheck shutdown/pause and retry, dropping nothing.

| Metric | Before fix | After fix |
|---|---:|---:|
| TetherKit's own TX frame drops | 1889 | **0** |
| TCP TX retransmits | 3829 | **0** |
| Bidirectional concurrent TX | 4.8 Mbps | **87 Mbps** |
| Unidirectional TCP RX (regression check) | 324-327 | 326-327 |

Two honest notes: bidirectional RX dropped from 320 to 240 -- that is not a regression but a restoration of fairness (before the fix TX was starved and RX monopolized the link; the total is still ~327 Mbps). Also, the bidirectional collapse previously attributed to "bufferbloat" was mostly not bufferbloat: RTT inflation still exists, but once frame drops were fixed TX recovered from 4.8 to 87 Mbps.

**Also invalidated one old tuning suggestion**: before the fix, raising `--tx-transfers` to 16 could cut drops to about 1/4, but that was using pool depth to compensate for "refusing to wait". After the fix, 4 / 8 / 16 were measured three times each with **no distinguishable difference**, so the default remains 4.

Warning: two statistics miscounts were fixed along with this: oversized frames and frames shorter than the Ethernet header were previously counted as "sent" (`SendFrames` returned only one number and the comment claimed the caller could infer drops, but it actually could not); when `SendFrames` returned an error, the rest of the batch went into no counter at all and simply vanished.

## 7. Known pitfalls and mitigations (**write pitfalls here when you hit them; do not hit them twice**)

1. **The cache line is 128 bytes**, not the habitual 64. If an SPSC queue is aligned to 64, the producer and consumer indices still land on the same cache line and false sharing remains. The project uses `kCacheLineSize = 128` everywhere.
2. **`std::format` requires a deployment target >= 13.3**, otherwise it reports `to_chars unavailable`. CMake enforces this.
3. **`std::hardware_destructive_interference_size` does not exist in Apple libc++**; do not use it.
4. **BPF has no zero-copy**, do not look for `BIOCSETZBUF`. But **batch writes do exist** -- see the next item.
4b. ~~"Darwin BPF does not support batch writes" was wrong.~~ The conclusion originally recorded in section 2 has been corrected: macOS 14+ has the private ioctl `BIOCSBATCHWRITE`, which can send multiple frames in one `write()`. This project implements it with feature detection (`BpfLink::WriteFramesBatched`) and falls back to per-frame write automatically on macOS 13 and earlier.
5. **BPF `BIOCSBLEN` must be set before `BIOCSETIF`**; the wrong order means the buffer size does not take effect.
6. **BPF traversal must use `bh_hdrlen`**, not `sizeof(struct bpf_hdr)` -- the header is followed by alignment padding.
7. **libusb has no `detach_kernel_driver` on macOS**. If an interface is held by a kernel driver, the only options are a codeless kext / dext or re-enumeration; libusb cannot solve it.
8. **Do not assume a device or root is present when tests run**, so "it does not run" does not mean "the code is wrong"; everything verifiable offline must be covered by mock tests, and tests that need root must be able to skip cleanly.
9. **Never put quotes around arguments in ctest's `add_test`.** Writing `COMMAND tetherkit_tests --test-suite="${_suite}"` causes CMake to pass the quotes as part of the argument content (`ctest -V` shows `"--test-suite="foo""`), doctest matches no cases -> 0 cases run -> doctest returns exit code 0 for zero matches -> ctest reports Passed. **The entire test suite silently became a no-op while staying all green**, actually hiding 4 real failures. The correct form is `--test-suite=${_suite}` (no quotes).
10. **When adding a "must hit at least one assertion" guard to a ctest case, use `FAIL_REGULAR_EXPRESSION`, not `PASS_REGULAR_EXPRESSION`.** The latter **replaces** exit-code evaluation (CMake's documented behavior); once set, a real assertion failure is ignored instead -- digging the previous pitfall right back open. `FAIL_` is additive on top of the exit code.
11. **Time-related classes must not read the clock in their constructor.** `PeriodicTimer` used to do that, which meant the instant read in the constructor was slightly later than the caller's `now`, so "now + period" had not yet elapsed and unit tests failed randomly and non-reproducibly. Changed to take the timing origin explicitly (the default value keeps the convenient form).
12. **Warning: synchronous libusb interrupt transfers block forever on macOS; the timeout parameter is not honored at all.** Once hit, the symptoms are a stuck control thread, no more statistics output, no response even to SIGTERM, and leftover feth interfaces on exit. The stack looks like this:
   ```
   Poll -> WaitForNotification -> do_sync_bulk_transfer
        -> sync_transfer_wait_for_completion -> handle_events -> poll(infinity)
   ```
   Two layers in the cause chain (both verifiable in libusb source): (1) the darwin backend marks all transfers with `USBI_TRANSFER_OS_HANDLES_TIMEOUT`, so `libusb_get_next_timeout` skips them and returns "no timeout", and the `poll()` in the synchronous wait blocks indefinitely; (2) on the IOKit side, darwin's `submit_interrupt_transfer` uses **`ReadPipeAsync` (the no-timeout variant)**, not `ReadPipeAsyncTO` used by bulk -- so the interrupt transfer's timeout **never takes effect at all**. **Changing timeout from 0 to 1 ms does not fix it**: layer (2) means it is ineffective for interrupt endpoints from the start. The only correct fix: submit a standing **asynchronous** interrupt transfer, let it complete on the event thread, and have `WaitForNotification` only check an atomic flag so it never enters libusb's wait path. -> Implemented this way; see `UsbControlChannel::StartNotificationListener`.
13. Also remember: `timeout = 0` means **wait forever** in libusb/darwin, not "do not wait". To "just probe", use a non-zero minimum value (`kProbeOnlyTimeoutMillis`), and as noted above this still does not work for interrupt endpoints.
14. **Without setting `BIOCSHDRCMPLT = 1`, a BPF `write()` to feth returns `ENXIO` ("Device not configured") directly -- it is not as mild as "the frame header gets rewritten".** A controlled experiment confirmed this: same code, same interface, the only difference was whether this ioctl was set -- without it `ENXIO` every time, with it `write` succeeds immediately. The original comment in `bpf_link.cc` only said `hdrcmplt=0` would "strip the first 14 bytes and rebuild the frame header"; that is the **semantics** of `hdrcmplt`. The **actual consequence** on feth is that the write does not work at all (`if_fake`'s output path cannot handle the `AF_UNSPEC` rebuild branch). When debugging `ENXIO` it is easy to assume the interface is not up or the name is wrong -- check this ioctl first. In ordering it must come before `BIOCSETIF`, and batch write (`BIOCSBATCHWRITE`) requires it to be 1.

15. **Warning: `osascript ... with administrator privileges` swallows inter-process SIGTERM delivery.** When using it for elevation testing, `kill -TERM $pid` inside the script returns 0, the target process's `blocked` and `pending` masks are both 0, and the handler installed by `sigaction` is present (sample shows the handler address is not `SIG_IGN`), yet **the signal never arrives** and the process can only be `kill -9`'d. A 15-line C program served as a control: plain shell OK, plain `osascript` OK, add `with administrator privileges` fails. -> Consequence: **do not use this elevation path to verify graceful shutdown**; it produces a false "shutdown hangs" failure that has nothing to do with the code under test (the run logs before and after the fix were all `Killed: 9`, which was once mistaken for a newly introduced regression). To verify end-to-end shutdown, run `sudo build/bin/tetherkit-cli` in a real terminal and press Ctrl-C -- that has been verified to print "stopped" with no feth residue.

16. **A "deliberately done this way" comment can still be wrong -- especially when it sounds convincing.** The root cause of TX frame drops (section 6.5) hid for an entire release because that drop logic was accompanied by a confident comment: "waiting would let the kernel buffer pile up into invisible drops". Both premises were wrong: `bs_drop` is read back and shown in the statistics line on every batch; and the 4 MiB kernel buffer is exactly the level that should absorb bursts. -> Lesson: **when writing "deliberate", be able to state the magnitude**. Here, a quick calculation of "one 256-frame slice needs about 26 transfer slots while the pool has only 4" would have made the problem obvious immediately. When reviewing "deliberately / on purpose", first check its quantitative assumptions.

17. **For "best-effort" fields, an empty value must not overwrite a known good one.** The defect where the device name degraded to VID:PID after connecting was three layers deep: string descriptors cannot be read while the device is occupied (empty string), the GUI happened to refresh the device list once in the window between "connect clicked" and "status polled to running" (empty string overwrote good data), and the list froze after running (the degraded name was fixed for the rest of the session). The fix does not try to block the race window -- there is always a gap across an XPC round trip, and it cannot be blocked completely -- instead it makes empty strings stop appearing: `tk_list_devices` remembers the last successfully read strings for each device keyed by "bus + address + VID:PID" and backfills when a read comes up empty; when the device leaves, the memory is cleared (to prevent an old name from attaching to a new device that takes the same address). **"Could not get it this time" is not the same as "the device has no name"**; the same applies to all best-effort fields -- either the consumer falls back to the old value or the producer backfills, pick one, otherwise a transient failure becomes a persistent data degradation (pure logic lives in `ReconcileDeviceStrings`, with a unit test in capi.support). The helper's occupancy check was fixed along with this: the old "session is non-nil" rule was wrong in both directions -- during handshake the session is not registered yet (a concurrent enumeration would insert transfers into the control endpoint mid-handshake), while a failed/stopped dead session has already released the device (after unplug/replug the name could never be read again). Changed to "actually holds it": the sessionStarting flag + runState in {starting, running, stopping}.
18. **SwiftUI does not know that "a global table lookup" has changed.** After moving strings to runtime lookup, changing the language does not make any `@Observable` property appear to change, so view bodies naturally do not recompute -- the UI just stays in the old language. The fix is to make the language change itself an observable value (`AppModel.languageRevision` increments on every switch) and use it as an identity: the main window and the menu-bar panel both attach `.id(model.languageRevision)` to force the entire tree to rebuild. **`.commands { }` is more subtle**: every `Button` label inside is its own independent expression, and in practice (verified by reading menu item names via AppleScript) after switching language only the language menu itself changed -- because it read `languagePreference` and therefore had a dependency -- while the neighboring "Check for Updates…" stayed in the old language. The fix is to wrap that group in **one View** and read revision once in its body so the whole group recomputes together (see `AppMenuItems`). A variant of the same problem: **a `static let` that stores text is evaluated only once** and never updates after a language switch. Any static member that stores text must be a computed property (the three authorization hints on `AppModel` and `NetworkCard.dnsHint` both hit this).
19. **On macOS 26, window chrome is determined by `LC_BUILD_VERSION`'s `sdk`.** Measured: a `swift build` product was linked by SwiftPM as `sdk 14.0` (`-target arm64-apple-macos14.0` folded into LC_BUILD_VERSION), so on an all-Tahoe machine it took **legacy chrome** -- the traffic lights were 14x16 pt button frames, 20 pt spacing, drawing only ~12 pt circles inside; by contrast Hand Mirror (minos 14.4 / sdk 26.5) and Dropover (minos 13.0 / sdk 27.0) both use 14x14 pt button frames, 23 pt spacing, full-size circles. All AppKit windows draw the same `_NSTheme*Widget` set; the difference is only SDK-gated. Fix: add `-platform_version macos 14.0.0 26.5.0` when linking the `TetherKitApp` target (gui/Package.swift), **keeping minos at 14.0 so only chrome is affected**. Every release package must be checked: `otool -l <binary> | rg -A4 LC_BUILD_VERSION` -- `sdk` must be >= 26. The main window was also changed to an AppKit-managed `NSWindow` (MainWindowManager): it is presented deterministically at startup and no longer depends on SwiftUI scene instantiation timing. Traffic-light style is independent of window ownership and is determined by the `sdk` above. `build-gui.sh`'s self-check now enforces this verification (LC_BUILD_VERSION sdk stamp >= 26); one packaging run verifies it.
20. **Window presentation for `.prohibited` / dev runs**: the main window no longer comes from a SwiftUI `Window` scene but is created and `makeKeyAndOrderFront`'d by the delegate in `applicationDidFinishLaunching` via `@NSApplicationDelegateAdaptor` -- a bare run still pops the window and no longer needs manual rescue from the menu bar; gatekeeping code such as `isWindowPresentationExpected` was removed entirely (window presentation is managed by MainWindowManager, and SwiftUI has no scene left to recreate on its own). The `.prohibited -> .regular` self-check in `TetherKitApplication.init()` is kept: it does not control window presentation, it controls normal activation semantics for an unactivated process.
21. **SwiftPM pinning `sdk` to the deployment target is a systemic issue.** Any SwiftPM project built without `-platform_version` will be treated as a legacy app on Tahoe; Homebrew builds are affected the same way -- if a formula build omits that flag, users still get legacy traffic lights.
22. **macOS 26 wraps view updates from Button actions in an animated transaction (button activation context).** Clicking the sidebar to switch pages made the new page briefly scale up by about 8-10% and then settle, triggered only by clicks; the same state change driven by a timer was pixel-clean. `Transaction.disablesAnimations` only prevents new implicit `.animation` writes into the transaction and **does not suppress transitions** -- a transition interpolates only when the transaction is animated (objc.io's Transaction / transitions posts) -- so a page write wrapped in an activation transaction is always interpolated, and `.transition(.identity)` / an instant transaction only make the jump faster without removing the root cause. Fixed in two places (source comment "triple clamp"): `SidebarRow` switches to `InstantButtonStyle` (`PrimitiveButtonStyle`): `.transaction { animation = nil }` + `.contentShape(Rectangle)` + `.simultaneousGesture(TapGesture().onEnded { trigger() })`, so no activation context is created at all (call `trigger()` on the configuration, not `action()`); `SidebarShell.select` moves the state write to the next runloop tick (`DispatchQueue.main.async`) with an instant-transaction backstop. See "Why page switches have zero animation" in docs/GUI-ARCHITECTURE.md.

23. **macOS 26 synchronizes "content size changes" with "window frame animation"** (WWDC25-256, release notes 61158194), and the default `sizingOptions` on `NSHostingView` push each page's intrinsic size into the window -- different page heights mean every page switch becomes a window-resize event source. Fix (`MainWindowManager`): `hosting.sizingOptions = []` must be set **before** attaching the contentView; `minSize` / `maxSize` are pinned to fixed values. Warning: on macOS 26, min/max are **reset to unset** shortly after the window is shown, accompanied by a +32 pt chrome settle (call stack `_setFrameCommon:display:fromServer:`) -- so the delegate idempotently re-pins them in `windowDidBecomeMain` / `windowDidResize`; the idempotent write also prevents self-recursion. The window `styleMask` never includes `.resizable`; min/max are used only to prevent programmatic changes. Warning: the reverse "correct the frame" approach does not work: calling `setFrame` to correct the frame from 592 back to the designed size of 560 is immediately undone by the settle, which stretches it back to 592 and resets min/max, looping until SIGTRAP. Idempotent min/max re-pinning is the end state; do not touch the frame.

(6) `ButtonTurn` moved into TetherKitUIModel (executable targets cannot be imported by `swift test`), and the commit semantics of activation escape have 6 unit tests (TetherKitUIModelTests/ButtonTurnTests).
    Round 9 (live recheck overturned r8's FKA-off Tab contract): (1) under keyboard navigation the Tab cycle originally did not enter the sidebar (row `.focusable(false)`), so as long as any control held focus, the "focus is empty/window itself" precondition for the window arrow-key claim failed -> Tab could not reach the sidebar and arrow keys were stranded (user live report). The contract reversed: row `.focusable(true)` became constant -- the r8 probe-matrix expectation "Tab never lands on a row" is obsolete from this point and the probe matrix must update its expectations first; FKA-off inertness no longer comes from the modifier chain but from activation-action branching: inside the FKA-off gate, native activation driven by the keyboard (live keyDown) is discarded and mouse events pass through, distinguished by `NSApp.currentEvent` type. Warning: `currentEvent` is read in two places (this gate and `ButtonTurn.write`'s defer decision), both only as a negative/branching signal -- an AXPress turn can leave a stale old event behind (this pitfall round 6), so do not use it as a positive predicate. (2) Return live-failure follow-up: the AX self-read claimed by the window's `performKeyEquivalent` could resolve a row in the synthetic probe but could not resolve one under the user's live FKA -> Return silently fell through. Added the focused row's own `.onKeyPress(.return)` (FKA-on gate, calling `rowSelect` directly), with zero AX-read dependency -- a headless environment cannot bypass the HID layer, so which link in this chain breaks on live hardware can only be verified on live hardware; the two claim levels are first-to-consume, and at worst the duplicate is an idempotent page switch. Numpad Enter (keycode 76) is still covered only by the window claim (SwiftUI `KeyPress.Key` has no numpad variant).
    Round 10 (self-driven keyboard-ring exploration, superseded in Round 11): Warning: Round 10 explored claiming bare Tab at the AppKit window layer, maintaining a self-driven keyboard ring in `AppModel.sidebarRingRow`, and using `SidebarFocusBridge` for probe sampling. That design was proven over-engineered and blocked the normal focus order in Round 11 and has been completely removed; no residue such as `sidebarRingRow` remains in the code, do not reintroduce it.
    Round 11 (final architecture: native focus-cycle traversal and arrow-key activation in all states): (1) Root cause identified: the dead end that kept the probe from entering the sidebar was the `.focusable(SelfAccessibility.isFullKeyboardAccessOn)` bound on the `rows` container (which marked the whole group unfocusable when FKA-off); focusable removed from the container, only the selected row declares `.focusable(isSelected)` when FKA-off (all rows focusable when FKA-on). The Tab key now forms a "selected sidebar row <-> content buttons" bidirectional native Tab cycle directly. (2) Arrow-key activation: the `handleArrowKey` guard was changed to pass through for text editing (cursor movement) only when `isFirstResponderEditableText` is true; when a button/card/scroll area has focus, arrow keys step pages directly at any time, page switches self-heal focus, and the user is never stuck on the current page. The container `.onKeyPress` keeps up/down arrow keys as a backstop. With FKA-on, arrow keys are taken over by the system focus engine (the HID-layer "Move Focus" keys), so neither the window claim nor the container backstop receives the events; arrow keys move key focus itself -- expected behavior, not a defect. (3) Return claim and row-level backstop: when the first responder is not a field editor, the window's `performKeyEquivalent` attempts an in-process system-level AX focus resolution (requires TCC trust); if untrusted or no row is resolved, the event falls through to the focused row's own `.onKeyPress(.return)` backstop to switch pages. (4) Explicit focus highlight: when any row has focus and the window is active (`controlActiveState == .key`) it shows an accent border and a light-gray background; when the window loses focus to the background the border is removed automatically. The selection follows arrow-key movement in sync.
25. **A required-status-check rule on `main` changes how you work, and `strict` makes it worse.**
    The repo's own history is 145 direct commits to `main` against 5 merge commits, so direct pushes are the normal way work lands here. Adding `required_status_checks` to `main` rejects a direct push: the checks have to have passed on that commit *before* the push, which means the commit has to live on a branch first. That is not a subtle effect, it changes the workflow. `strict_required_status_checks_policy: true` compounds it: the topic branch must be up to date with `main`, so every PR needs a merge or rebase of `main` into it first, and the checks re-run. On a repo where `main` moves often, that is the difference between "merge my PR" and "merge `main` into my PR, wait for CI, then merge my PR". The maintainer's choice for this repo is PR-only, so `strict` is off and the checks are the loose kind: the branch does not have to be current, and the checks that ran against the branch head are what gate the merge. Warning: the required-check list is matched by **check-run name**, so a matrix-expanded name (`macos-26 · Release`, `feth private-ABI check · xcode-27`) is brittle -- adding an Xcode leg or a build type changes the names, and a required context that never reports blocks a PR forever with no useful error. The names here were taken from live check-runs rather than typed by hand, and they carry `integration_id: 15368` (github-actions) so no other app can satisfy them. When the matrix changes, update the ruleset's context list in the same commit.
26. **The token that writes the tap's `main` is not what stops it -- the tap's ruleset is.**

    The tap update pushes to `justsrc/homebrew-tap`, a different repository, so `GITHUB_TOKEN` cannot reach it. One fine-grained token scoped to that tap does the whole job: clone over https, push the bump branch, open the PR. That token CAN write the tap's `main` directly, and nothing in the credential stops it.

    What stops it is the **tap repo's own ruleset**, which requires changes to land as a pull request. Proven, not assumed: with a write-scoped credential in hand, a direct push to the tap's `main` was rejected with "GH013: Repository rule violations found... Changes must be made through a pull request", and `main` did not move.

    So do not describe a credential split as the review guarantee. A credential controls the blast radius of a leak; the ruleset controls whether unreviewed code can reach the tap. Two different properties, two different mechanisms, and only one of them is the guarantee.

    One credential rather than two is the simpler shape: one secret to provision, one to rotate, one capability to reason about when it leaks.

    One residual is worth naming so nobody mistakes it for a bug: the token's `contents:write` also reaches the tap's **tags and releases**, which no ruleset governs (the tap's ruleset gates branches only). Fine-grained tokens have no narrower grant that still allows branch pushes plus PR creation plus file writes, so this cannot be tightened -- it can only be documented, and it is bounded by the token's own scope.

27. **`commit.signoff` is not a git config key, and `web_commit_signoff_required` does not gate CLI pushes.**
    Two adjacent traps that both look like "sign-off is on now". (1) `commit.signoff` does not exist: git 2.56's binary carries only `format.signoff` (which governs `format-patch`, not `git commit`). Setting it reads back cleanly and does nothing, while `git commit -s` does add the trailer. So the thing worth checking is whether the trailer is in the message, never whether the config key is set. (2) `web_commit_signoff_required` governs commits made through the **web interface** only, per the field name and GitHub's docs; it never rejects a CLI push. Enabling it is a two-minute change with no effect on a maintainer who pushes from the terminal, so do not read it as "sign-off is now enforced on my commits".

28. **A token in a git remote URL leaks three ways, and only one of them is the file.**

    The pattern `git remote set-url origin https://x-access-token:$TOKEN@github.com/owner/repo.git` puts the credential in three places, and the obvious one is the least interesting:

    1. **`.git/config`**, which persists for the life of the clone and is readable by anything that can read the file.
    2. **The process argument list**, where `ps` shows it to every user on the machine.
    3. **The failure message.** This is the one that bites in CI. A wrapper that raises `subprocess.CalledProcessError(returncode, command, ...)` embeds the whole command list in the exception, the traceback prints it, and the CI log prints the traceback. The token lands in the log, where it is not masked unless GitHub happens to know the exact string.

    Point 3 is why "we set the URL and then unset it again afterwards" is not a fix. The unset only protects the file; the argv exposure and the error path are untouched.

    The fix that removes all three is a **credential helper**: the token lives in the environment, git asks a helper for it at the moment it needs it, and the helper is the only thing that ever sees the value.

        git config --local credential.helper ""
        git config --local credential.https://github.com.helper '!gh auth git-credential'
        GH_TOKEN=$TOKEN git push

    Facts measured while fixing this, all against the real tap:

    - `gh auth git-credential get` serves `GH_TOKEN` from the environment, and `GH_TOKEN` **outranks** `GITHUB_TOKEN`, so the helper uses the tap token and not the workflow's own `GITHUB_TOKEN`. The precedence is the whole reason this works: the workflow's `GITHUB_TOKEN` cannot write to another repository, and it is set in the same environment.
    - The empty `credential.helper` value is what **resets** an inherited helper list. Without it, a helper from the machine's global config is consulted first. Proven against a deliberately hostile global helper.
    - `gh repo clone` leaves **no** credential in `.git/config` (it uses a temporary helper), so the clone never needed the URL rewrite in the first place.
    - The push must run with the token in its environment. A `git push` that inherits the step's `GH_TOKEN` would use the wrong token, and the failure is a 403, not a prompt.

    Any script that pushes with a credential must do the same: the safe default is to have no script anywhere embed a token in a URL.
